Behaviour: one GeoPackage per site (`<site>.nsgeo.gpkg`) with four tables.
`grids`/`lines`/`marks` are derived from the session (regenerated by
`truncate()` + `addFeatures()` through the already-loaded QGIS layer's data
provider — the file itself is never touched) and set `readOnly()` in QGIS.
`picks` is authored, created once, and never refilled. The package CRS is
the first grid's; other grids are transformed into it via
`QgsCoordinateTransform` at write time. `lines` gets a categorised
per-grid renderer.

## Deviation from the brief, with reasoning

**The brief's reference `refill_lines`/`refill_marks` do not guard
`Line.trace_coords(frames)`.** The brief's own "sharp edges" section says
this call raises `ValueError` for a time-triggered line
(`traces_per_metre <= 0`), and explicitly requires: "A single unplaceable
line must not abort the whole layer build — degrade that line, keep the
rest." The reference code as given does not do this — the call is bare,
inside the per-line loop, with no `try`/`except` around it.

I fixed this by adding `SiteLayers._line_points(line, grid, frames)`, which
wraps `line.trace_coords(...)` in `try/except ValueError`, logs a warning
via `QgsMessageLog`, and returns `None` for that one line; both
`refill_lines` and `refill_marks` skip (degrade) a line when this returns
`None` and continue with the rest.

**Why this needed fixing, not just noting:** I initially assumed the
consequence of the bug would be an exception propagating straight out of
`session.add_lines(...)` to the caller (which would make a naively-written
test fail loudly and obviously). Measuring it directly showed the real
consequence is worse: `session.add_lines()`/`add_grid()` etc. emit Qt
signals with **direct** (synchronous, same-thread) connections, and PyQt5
does not propagate an exception raised inside a directly-connected slot
back to the emitter — it prints the traceback to stderr and returns as if
nothing happened. So the unfixed reference code doesn't crash; it silently
aborts `refill_lines()`/`refill_marks()` partway through the per-line loop
(before ever reaching `_refill(...)`), leaving the GeoPackage table
**stale** — any line after the bad one in iteration order, even a
perfectly good one, silently never gets written, with only a stderr
traceback as evidence. This is exactly the "keep the rest" failure the
brief's sharp-edge section warns about, just manifesting as silent
staleness rather than a loud crash.

This also affected how I had to shape the two tests that prove it (see
below): a test that only checks "feature count unchanged, bad key absent"
cannot tell correct per-line degradation apart from a silent whole-table
abort, because both produce the same stale count. The tests add the bad
line *and* a new good line in the same `add_lines()` call (bad line first
in iteration order) and assert the good line **is** written — that's the
assertion the buggy version fails and the fixed version passes.

### What changed, per finding

**Finding 1 (package CRS frozen at the first grid).** `ensure_tables()`
now calls a new `_ensure_table()` for every table on every refresh, which
compares the table's *on-disk* CRS and field names (via a new
`_table_schema()` helper) against the current target (`crs()`'s current
value, and `TABLES[name]`'s field spec). If either has drifted, the table
is rebuilt: for `picks`, rows are read out first (`_read_picks_rows()`),
geometry transformed into the new CRS via `QgsCoordinateTransform`, then
the table is dropped (`_drop_loaded_layer()`, which removes the tracked
`QgsVectorLayer` from the project before recreating the file-level
table — rule 2, never two OGR handles on the same table) and recreated,
and the migrated rows written back in. `grids`/`lines`/`marks` are
simply recreated empty, since `refresh()` calls `refill_grids/lines/
marks()` immediately afterward anyway.

Decision recorded (the brief's Finding 1 offered two options): **transform
and carry picks across, recreate-and-refill the derived tables** — not
"refuse loudly" — because picks are the one table with no other source of
truth, and a CRS edit through Task 9's dock should not need the user to
re-pick anything.

*A real bug found while building this fix, not merely reference-code
review*: my first version built the migrated `QgsFeature` objects against
`_fields(spec)` — the same helper `_create_table` uses — rather than the
newly (re)created layer's own `.fields()`. A GPKG table always carries an
implicit leading `fid` column that `spec` never lists, so a feature built
one field short of the provider's real field list had every attribute
land one column over on insert. Measured directly: a pick's `line_key`
("hello") came back reading as its `time_ns` value ("5"), and `time_ns`
itself came back `NULL`. Fixed by reading old rows as plain
`{field_name: value}` dicts (`_read_picks_rows`, not tied to any
particular `QgsFields` object) and building the final `QgsFeature`
against the *real*, freshly-opened layer's `.fields()`. Verified via a
standalone probe before and after the fix (see TDD Evidence).

**Finding 2 (`feature_count("picks")` returns -1).** Reproduced exactly as
described: a table this session's refills never write to can report `-1`
from `featureCount()`/`dataProvider().featureCount()`, both for a
brand-new table and a reopened one, with a GDAL "unable to open database
file" stderr error accompanying it. Investigated the suggested fix
(`layer.reload()`) directly: calling it immediately after opening each
table, or once after opening the whole batch within the same
`ensure_tables()` call, did **not** reliably clear it in this exact
reproduction — it took one further `reload()` call, at an unpredictable
point, to actually clear the cache. I could not reproduce reviewer's
"verified to fix it permanently" as an unconditional guarantee, so I did
not build correctness on top of it. `ensure_tables()` still does one
`reload()` pass over every newly-opened table (cheap, sometimes helps,
matches the reviewer's suggested primary approach, and may help a user
who reads `dataProvider().featureCount()` directly through QGIS's own UI
rather than through `feature_count()`), but the actual guarantee is
`feature_count()`'s fallback: when the cached count comes back negative,
it counts `getFeatures()` directly. New test reopens a saved site with
one pick and asserts `feature_count("picks") == 1`.

**Findings 3 and 4 (refresh() has no error containment; a layer deleted
from the project breaks the next refresh and detach()).** Both stem from
the same root cause the dispatch already flagged for `_line_points`:
PyQt5 does not propagate a slot's exception back to whatever emitted the
signal, it prints it to stderr and returns as if nothing happened.
`refresh()` now wraps each of `refill_grids/lines/marks()` in its own
`try/except Exception`, logging via `QgsMessageLog` on failure (rule 4,
added to the module docstring) — a stale schema, a `RuntimeError` from
`_refill` (e.g. a Windows file lock), or anything else in one table no
longer prevents the other two from refilling. `_ensure_table`'s schema
check (Finding 1's mechanism, generalized to compare field names too, not
just CRS) also means the reviewer's specific repro — a `lines` table
missing `grid_id` raising `KeyError` deep in `refill_lines` — now
self-heals before `refill_lines` ever runs, rather than needing the
`try/except` as a safety net for that particular case; the `try/except`
still matters for failure modes schema-repair can't prevent (proven via
the monkeypatch-based containment test, since a real repro that isn't
already prevented by the schema check is hard to construct honestly).

For the layer-deletion hazard: `SiteLayers.__init__` now connects
`project.layersWillBeRemoved` to `_on_layers_removed`, which drops any of
our tracked names whose layer id is in the about-to-be-removed list —
while the layer is still safe to call `.id()` on, since it's a
*pre*-removal signal. The underlying GeoPackage table is untouched (only
QGIS's in-memory layer is gone), so the next refresh's `ensure_tables()`
treats it as "not currently loaded" and reopens it fresh, exactly as for
a table that had never been loaded. `detach()` additionally guards every
layer and the group node with `sip.isdeleted()` before touching them, as
a second line of defense against a deletion path the signal doesn't
cover.

**Finding 5 (removing the last grid leaves stale derived-table data).**
`refresh()` now distinguishes "site closed" (`site is None`, do nothing —
`detach()` handles that via `site_closed`) from "site open but no grids"
(`not site.grids`): the latter calls a new `_clear_derived_tables()`,
which truncates `grids`/`lines`/`marks` for every table that has already
been created (nothing to do for a site that has never had a grid at all —
no file to touch). `picks` is untouched, matching every other refill.

**Finding 6 (the `ValueError` catch in `_line_points` was wider than
documented).** `self._points(...)` — the CRS transform — is now called
*outside* the `try`, which now wraps only `line.trace_coords(frames)`.
A `ValueError` from a bad shape or a broken transform is a real bug and
must surface, not be misreported as "this one line is unplaceable".

**Finding 7 (the picks-survival test didn't prove the refills ran).**
Added `assert layers.feature_count("grids") == 2` and
`assert layers.feature_count("lines") == 3` to
`test_picks_survive_multiple_refills_with_attributes_intact`, right after
its picks assertions, with a comment explaining why: a silently aborted
refresh (Finding 3) would have left picks looking exactly as "correctly
ignored" without ever having refilled anything.

**Finding 8 (`session.line_key(line)` recomputed per line per table per
refresh).** `refill_lines`/`refill_marks` now iterate
`self.session.keys()` and fetch each `Line` via `self.session.line_for_key(key)`,
reusing the key the session already resolved once at install time,
rather than calling `session.line_key(line)` (which calls
`Path.resolve()`) again for every line, in every table, on every
refresh. This also stops the two methods from iterating `site.lines`
directly, reading only through the session's public accessors.

## Fix round 3 (review response)

Commit: `1e8e6a1`, on top of `6718471`. All four findings addressed.
Files changed: `packages/nsgeo-qgis/nsgeo_qgis/layers.py`,
`packages/nsgeo-qgis/tests/qgis/test_plugin_layers.py`.

This round's framing from the coordinator was pointed and correct: two
rounds in a row, closing every named finding introduced a new one of the
same class, because each fix was checked against the scenario it was
written for and not against what its *own* new code does when it fails.
The contract for this round added a required deliverable beyond the four
fixes: a line-by-line failure-path audit of the new code, included below
in full rather than only as code comments.

### What changed, per finding

**Finding 1 (a table whose prep failed is still refilled with wrong-CRS
geometry).** `ensure_tables()`'s per-table `try/except` (round 2) logs a
failure but never recorded *which* table it was, so `refresh()`'s refill
loop had no way to know grids/lines/marks needed skipping. Rather than
threading a set of failed names from `ensure_tables()` into `refresh()`
(more state to keep in sync, more places for the two to drift apart), I
used the reviewer's second offered option: `_refill()` -- the one place
every one of the three refills already passes through -- now refuses
when `layer.crs() != self.crs()`, raising before `truncate()` ever runs.
A table that failed its own prep this cycle necessarily still declares
its old CRS, so this catches exactly the failed table without either
side needing to track anything extra. The one call site that must *not*
be caught by this (`_clear_derived_tables()`, called when there are no
grids left at all) has no target CRS to compare against --
`self.crs()` is `None` there by construction -- so the guard is written
to pass through whenever `target is None`, matching that call's own
"there is nothing to compare against, and every reason to proceed"
reasoning rather than adding a separate bypass flag.

**Finding 2 (a leftover `_PICKS_BACKUP` wedges every future rebuild
forever).** My round-2 report called this "cosmetic, self-correcting" --
wrong on both counts, and the reviewer's measurement showed it plainly:
the backup is created *only* by a rename, nothing ever renames or drops
it away again on its own, and the very next rebuild's rename-out step
needs that exact name free. Fixed with a new `_drop_table_if_exists()`
(best-effort: swallows any failure, since the operation that actually
needs the name free -- the rename right after it -- fails loudly on its
own account if the name is somehow still taken), called immediately
before the rename-out in `_rebuild_picks`.

**Finding 3 (process death between the two renames strands the rows,
invisibly).** My round-2 docstring claimed a failure "anywhere in this
method" left a fully-populated `picks` table on disk -- true within one
call, false across a process restart, since there is no code left
running after the process dies to rename the original back. Added
`_recover_picks_backup()`, invoked from `_ensure_table` exactly when
`picks` is reported missing: if `_PICKS_BACKUP` exists, rename it back
into `picks` before deciding whether a rebuild is still needed (re-
probing its schema afterward, rather than assuming the state prior to
the interrupted rebuild). If the CRS/schema mismatch that started the
original rebuild is still there, `_rebuild_picks` runs again from the
recovered, consistent state -- not from an empty table.

**Finding 4 (leaked message-log connection).** Replaced the ad hoc
`QgsApplication.messageLog().messageReceived.connect(...)` in the round-2
test with a `message_log` fixture that disconnects on teardown, and
moved the existing test that needed it onto the fixture.

### The failure-path audit (the deliverable itself)

Every new line added this round, and what happens if it fails:

**`_refill()`'s CRS guard** (`if target is not None and layer.crs() !=
target: raise RuntimeError(...)`):
- *Can it itself fail unexpectedly?* `self.crs()` is unchanged,
  pre-existing code. `layer.crs()` on a layer whose C++ object has
  since been deleted (round 1's Finding 4 scenario) raises
  `RuntimeError: wrapped C/C++ object ... has been deleted` -- but the
  very next line in the *unchanged* code (`layer.dataProvider()`) has
  exactly the same exposure already; this guard doesn't add a new
  failure surface, only moves the first risky call on `layer` a few
  lines earlier.
- *Who catches it?* Whichever of `refill_grids`/`refill_lines`/
  `refill_marks`/`_clear_derived_tables` called `_refill` -- each
  already wrapped in its own `try/except` by `refresh()` (round 1).
- *What state does it leave?* The layer is untouched: the guard fires
  before `provider.truncate()`, so a refusal never leaves a table
  half-written.
- *What does the user see?* A `Qgis.MessageLevel.Critical` log entry
  naming the table and both CRSs, exactly like every other refill
  failure already logs.

**`_recover_picks_backup()`** (called from `_ensure_table` only when
`picks` is reported missing):
- *`_table_schema(path, _PICKS_BACKUP)` failing?* It is the same,
  already-audited (round 1) static method used for every table; no new
  exposure.
- *The `_log(...)` call firing before the rename is attempted, then the
  rename failing anyway?* The message says "restoring it before
  continuing" at the point of *attempting* it, not asserting success;
  the outer `except` in `ensure_tables()` logs the actual
  `renameVectorTable` failure right after with the real error, so the
  two messages together are accurate even though the first is written
  before the second could still contradict it.
- *`conn.renameVectorTable("", _PICKS_BACKUP, "picks")` failing?*
  Uncaught locally, propagates through `_ensure_table` to
  `ensure_tables()`'s per-table `try/except`, logged. State: the backup
  is untouched (a failed rename is a no-op at the SQLite level, not a
  partial one), `picks` is still missing this cycle, and the next
  refresh retries from the same, still-recoverable starting point.
- *The re-probe (`existing_crs, existing_fields =
  self._table_schema(path, name)` right after a successful recovery)
  somehow still not finding `picks`?* This is the one gap I chose not to
  engineer around: if the rename genuinely succeeded (no exception) but
  the immediately following fresh `QgsVectorLayer` open still can't see
  it, `existing_crs` stays `None`, `_ensure_table` falls through to the
  plain "doesn't exist, create fresh" branch, and the just-recovered
  rows would be silently orphaned under a name nothing references again.
  I judge this as outside the trust model the rest of the module already
  runs on (a `QgsProviderRegistry` DDL call that returns without raising
  is assumed to have taken effect, immediately and visibly, everywhere
  else in this file too) rather than a gap specific to this new code,
  and did not add a retry/verify loop for it.

**`_drop_table_if_exists()`** (`with contextlib.suppress(Exception):
conn.dropVectorTable("", name)`):
- *Swallowing a real failure (not "doesn't exist") silently?* Yes,
  deliberately, and audited for consequence: the very next line
  (`conn.renameVectorTable("", "picks", _PICKS_BACKUP)`) needs that same
  name free, so if the drop silently failed for a real reason (not
  simply "nothing there"), the rename fails immediately after, loudly,
  with its own clear error ("table already exists") -- caught and logged
  by `ensure_tables()`'s existing containment. Nothing is lost by the
  swallow; at worst, a genuine drop failure now surfaces one line later
  as a different, still-visible error, with no log line of its own for
  the original attempt. I judged adding a distinct log line for the
  swallowed exception as more noise than signal, since the rename's own
  failure message already names the actual blocker.
- *Could swallowing this exception leave the `conn` object itself in a
  bad state for the following calls on the same connection?* I could not
  rule this out from documentation alone and did not attempt to, since
  `dropVectorTable`/`renameVectorTable` are documented as independent
  DDL-style operations rather than steps of a transaction the caller
  manages; treated as consistent with how every other `conn` call in
  this method is already used.

**The call site in `_rebuild_picks`** (`self._drop_table_if_exists(conn,
_PICKS_BACKUP)` immediately before the existing rename-out): no new
control flow beyond the helper above; it runs inside the same method
whose every other line was already audited across rounds 2 and 3.
